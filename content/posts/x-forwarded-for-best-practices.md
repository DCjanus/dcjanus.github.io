最近排查一个权限问题时，发现部分本应该按外网请求处理的流量，被业务误认为来自内网。

最后定位下来，问题和一个非常常见的 Header 有关：`X-Real-IP`。

这类问题比较麻烦的地方在于，单看某一个 NGINX 配置，它可能没有明显错误；真正的问题来自长期演进后的入口、代理和业务假设没有保持一致。

## 问题是怎么出现的

当时有一类需求，需要根据请求来源判断是否允许访问某些内部能力。简单来说，内网请求可以少一些限制，外网请求需要更严格的鉴权。

公司的 HTTP 流量大多经过 NGINX。业务并不直接维护完整的 NGINX 配置，而是通过统一系统发布转发规则。这个系统会自动处理一些常见 Header，包括 `X-Real-IP` 和 `X-Forwarded-For`。

最初的问题比较直接：外部请求可以手动携带一个假的 `X-Real-IP`。如果入口没有正确清洗这个 Header，业务侧看到的来源 IP 就可能是攻击者指定的值。

但后续修复并没有完全解决问题。

外网入口改成强制覆盖 `X-Real-IP`，这个方向没有错。但它隐含了一个前提：入口边界必须清晰。哪个 NGINX 是真正的边缘入口，哪个只是内部转发节点，哪些 Header 应该覆盖，哪些应该继承，都需要有明确约定。

而实际环境里并不是这样。有些业务可以申请自己的 NGINX 和公网 IP，不同业务之间也存在复杂的调用关系。请求最终到达哪个入口，并不一定和设计时认为的一样。

例如：

```text
业务容器 A -> 外网入口 NGINX -> 业务容器 B
```

外网入口看到的 source IP 可能是业务容器 A 的内网地址，于是把 `X-Real-IP` 设置成这个地址。

业务容器 B 再读取这个 Header 时，只能看到：

```text
X-Real-IP: 10.x.x.x
```

于是它认为请求来自内网。

但实际上，这个内网 IP 只代表上一跳连接来源，并不代表整个请求链路可信。

## 单值 Header 的问题

`X-Real-IP` 最大的问题不是它不准确，而是它表达的信息太少。

在简单链路里：

```text
用户 -> NGINX -> 服务
```

它很好用。服务只需要知道连接自己的 NGINX 看到的客户端地址。

但链路复杂以后：

```text
用户 -> NGINX A -> NGINX B -> 服务
```

一个 IP 已经无法描述整个请求经过了什么。

`X-Forwarded-For` 的价值就在这里，它保留了代理链路中的来源信息。

例如：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP $remote_addr;
```

可能产生：

```text
X-Forwarded-For: 203.0.113.10, 10.0.1.12, 10.0.2.34
X-Real-IP: 10.0.2.34
```

前者至少保留了链路，后者只保留了最后一跳。

## X-Forwarded-For 也不是可信来源

这里容易产生另一个误解：既然 `X-Forwarded-For` 保存了完整链路，是不是就可以直接相信它？

答案也是否定的。

客户端完全可以自己发送：

```http
X-Forwarded-For: 10.1.2.3
```

所以真正可信的不是 Header 本身，而是可信入口追加的信息。

正确的做法通常是：入口节点清洗外部传入的 Header，然后追加自己看到的 source IP。

例如：

```text
X-Forwarded-For: 10.1.2.3, 203.0.113.10
```

业务侧不能简单相信最左侧的 IP，而应该根据自己的信任边界判断完整链路。

对于内外网权限判断，一个更保守的规则是：只有链路中的每一跳都属于可信范围，才按内网请求处理；只要存在外网 IP 或无法确认的节点，就按照外网请求处理。

这个规则依赖一个前提：入口节点的行为是可控的。如果入口本身不可信，任何来源 Header 都没有意义。

## 更大的问题是入口治理

这次问题表面上和 `X-Real-IP` 有关，但真正暴露出来的是入口治理问题。

单个业务配置看起来可能没有问题：

- 外网入口覆盖 Header；
- 内网入口保留链路；
- 业务根据 Header 判断来源。

但当入口数量增加、业务可以自由申请公网入口、调用链越来越复杂后，任何一个假设被破坏，都可能产生错误判断。

所以相比让每个业务自己理解各种 Header，更合理的方式是收敛入口：

- 明确哪些 NGINX 是边缘入口；
- 统一处理来源 Header；
- 明确哪些代理可以被信任；
- 业务不要自己推断复杂网络拓扑。

## 它不能证明用户真实来源

另外一个常见误区，是把 `X-Forwarded-For` 当作用户真实来源。

例如早期一些网站会根据 `X-Forwarded-For` 判断用户所在国家。如果后端直接相信这个值，用户只需要修改请求 Header，就可能绕过这种限制。

这和内外网权限判断是两个问题。

前者判断的是：请求链路里有没有经过可信内部网络。

后者判断的是：用户真实来自哪里。

用户可控的 Header 永远不能直接证明真实来源。

## 总结

`X-Forwarded-For` 和 `X-Real-IP` 本身都不复杂。

真正复杂的是企业系统长期演进后形成的入口、代理和业务假设。很多问题并不是因为某个人不知道 Header 可以伪造，而是这些约定没有被统一管理。

`X-Real-IP` 在简单链路下很方便，但它会把一条请求链路压缩成一个值。`X-Forwarded-For` 至少保留了链路信息。

对于内外网权限判断，这个差异已经足够重要。但对于更高权限的能力，来源 IP 仍然只能作为辅助条件，真正的边界应该来自身份认证、入口隔离和服务间授权。
