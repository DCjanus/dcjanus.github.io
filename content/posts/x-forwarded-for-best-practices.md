想写这篇文章，是因为 [`X-Forwarded-For`](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Reference/Headers/X-Forwarded-For) 这个 Header 太普通了，普通到很多人见过，但没有认真想过它到底适合解决什么问题。

企业内部一旦需要判断请求来自内网还是外网，很多人会选择一个看起来更直接的单值 Header，比如 `X-Real-IP`。这不是哪个公司的发明，在 NGINX 生态里也很常见。正常链路下能跑，问题也不明显。

但请求链路只要复杂一点，单值 Header 就容易丢掉关键上下文，甚至把外网请求误判成内网请求。我之前遇到过一次类似问题。

## 语义

`X-Forwarded-For` 和 `X-Real-IP` 都是常见的来源类 Header，差别主要在保留的信息量。常见 NGINX 配置大概是这样：

```nginx
# X-Forwarded-For: 203.0.113.10, 10.0.1.12, 10.0.2.34
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

# X-Real-IP: 10.0.2.34
proxy_set_header X-Real-IP $remote_addr;
```

`X-Forwarded-For` 会把每一跳看到的 source IP 追加下去；`X-Real-IP` 通常只保留当前连接的 source IP。前者至少保留了链路，后者在多跳代理里很容易把前面的信息抹掉。

## 当时的问题

当时我做的一类需求，需要判断请求来自机房内网还是公司外网。这个判断会影响权限：内网请求可以访问一些内部能力；外网请求需要更严格的鉴权，或者直接拒绝。

公司的 HTTP 流量大多经过 NGINX。业务不直接手写完整配置，而是通过统一的 NGINX 管理系统发布转发规则。这个系统默认会处理 `X-Real-IP` 和 `X-Forwarded-For`，业务方未必真的理解这两个 Header 的区别。

更麻烦的是入口边界。当时每个业务都可以申请自己的 NGINX 和公网 IP，很多 NGINX 节点都可能成为事实上的边缘入口。再叠加一些域名解析和调用链路问题，请求不一定走到它原本应该走的内网或外网入口。

最早的问题是外部伪造。攻击者从公网请求服务时手动带上一个内网 `X-Real-IP`，部分入口没有清洗，原样转发给业务。业务看到它落在内网网段，于是把外部请求识别成内网请求。

后来的修复也不是终点。外网入口改成强制覆盖 `X-Real-IP`，本身方向没错；但它要求入口角色非常清楚。哪个 NGINX 是边缘入口，哪个是内网转发节点，哪些 Header 应该覆盖，哪些应该继承或追加，都要分清。

当时恰恰不是这种状态。有些业务容器本来应该请求内网入口集群，但因为域名解析或配置问题，请求打到了外网入口：

```text
业务容器 A -> 外网入口 NGINX -> 业务容器 B
```

外网入口看到的 source IP 是业务容器 A 的内网 IP，于是把 `X-Real-IP` 覆盖成这个内网 IP。业务容器 B 再读取这个 Header，就会认为请求来自内网。但这可能只是业务容器 A 代替外部用户发起的调用。

这类问题麻烦的地方在于：单看某条规则，它可能是对的；但使用方足够分散时，总会有人把规则用在错误的位置。最后有的请求被改写成内网 IP，有的请求被改写成外网 IP，安全问题和可用性问题都会出现。

## 更稳妥的判断方式

`X-Forwarded-For` 更适合这类场景，是因为它保留链路。即使外部攻击者伪造：

```http
X-Forwarded-For: 10.1.2.3
```

入口仍然可以追加自己看到的 source IP：

```text
X-Forwarded-For: 10.1.2.3, 203.0.113.10
```

业务侧如果做的是“是否允许按内网请求处理”这种安全判断，就不应该直接取最左侧的 `10.1.2.3`。

如果一个外部用户请求先进入业务容器 A，随后业务容器 A 错误地请求了外网入口，链路可能变成：

```text
X-Forwarded-For: 203.0.113.10, 10.1.2.3
```

最右侧的 `10.1.2.3` 是业务容器 A 的内网 IP，但更早的外部用户 IP 还在。业务容器 B 只要检查完整链路，就不会因为最后一跳来自内网而把整个请求当成内网请求。

所以业务侧能做的，是尽量使用 `X-Forwarded-For`，并按完整链路保守判断：

```text
只有 X-Forwarded-For 里的每一跳都属于可信内网网段，才按内网请求处理。
```

换句话说，只要链路里出现外网 IP 或无法识别的 IP，就按外网请求处理。这个规则依赖一个前提：入口节点会清洗外部输入，并按约定追加自己看到的 source IP。

平台侧更应该做的是流量治理：把所有外网入口收拢到少数几个 NGINX 集群，严格控制这些集群上的规则，并让有经验的人审阅转发配置。入口散落在各个业务手里，总会有人把来源 Header 规则用错。

## 它不能证明真实来源

上面的规则只适用于内外网权限判断，不适合外推到真实来源判断。另一个常见误用，是把 `X-Forwarded-For` 当作用户地理来源。

早期微软 Bing 搜索里有一个小冰试用功能，当时按国家限制访问。那类限制不需要真的挂代理也可以绕过：装一个浏览器插件，把发往小冰的请求都加上一个合适国家的 `X-Forwarded-For`，后端如果直接相信这个值，就会把请求当成来自目标国家。

这和内外网权限判断是两类问题。内外网权限判断关心“链路中是否出现过不可信来源”；真实来源判断关心“用户到底从哪里来”。后者不能从用户可控 Header 里得出。

## 结尾

`X-Forwarded-For` 本身不复杂。真正复杂的是企业内部系统长期演进后形成的入口、代理、域名和业务假设。很多问题并不来自某个工程师不知道 Header 可以伪造，而是这个事实没有被落实到统一入口、代理约定和业务判断里。

单值 `X-Real-IP` 在简单链路下很方便，但它会把一条请求链路压缩成一个值。`X-Forwarded-For` 至少保留了链路本身。

对于内外网权限判断，这个差异已经足够重要。对于更高权限的能力，来源 IP 仍然只能是辅助条件。真正的边界应该来自身份认证、入口隔离和明确的服务间授权。
